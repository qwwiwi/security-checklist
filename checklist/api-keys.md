# API-ключи и секреты

API-ключ – длинная строка, по которой сервис (Anthropic, OpenAI, Supabase, платёжная система, облако) узнаёт, что запрос пришёл от вас, и выставляет вам счёт. Кто знает ключ, тот действует от вашего имени и за ваши деньги. Секреты – общее название для ключей, токенов (ключей доступа к ботам и сервисам) и паролей.

Ключи утекают не только через взлом: чаще их случайно отправляют в git (систему хранения истории кода), печатают в лог или вставляют в чат. Ниже – как это предотвратить и как быстро ограничить ущерб, если утечка всё-таки случилась.

| № | Что | Зачем | Как проверить | Как часто |
|---|-----|-------|---------------|-----------|
| K1 | Реестр ключей: какой ключ, где лежит, кто им пользуется, что он умеет, когда создан. Без самих значений | Без списка ключ нельзя быстро ни заменить, ни отозвать | файл-реестр есть и совпадает с тем, что лежит на серверах (сверяем имена, не содержимое) | Раз в месяц |
| K2 | Ключей нет в git, включая старую историю | Приватный репозиторий утекает вместе с любым взломанным аккаунтом или ноутбуком | `gitleaks git --redact` в каждом репозитории (`--redact` скрывает найденные значения); `git log --all --oneline -- .env "*.pem" "*.key"` – ждём пустой вывод | Раз в неделю |
| K3 | В GitHub включены secret scanning (поиск ключей в репозитории) и push protection (GitHub не даёт отправить код с ключом) | Ключ блокируется до того, как попадёт в репозиторий | Settings → Code security в каждом репозитории. Для приватных репозиториев функция может быть платной – тогда хватит gitleaks из K2 | Раз в квартал |
| K4 | Секреты хранятся вне кода, файл `.env` указан в `.gitignore` (список файлов, которые git не сохраняет), права на файлы 600 | Базовая гигиена: ключ не попадёт в git и не прочитается чужим процессом | `git check-ignore .env \|\| echo "нет в .gitignore"`; права – см. S8 в [servers.md](servers.md) | Раз в месяц |
| K5 | Отдельный ключ на каждого агента, каждый сервер и каждую среду (тестовую и рабочую) | Утёк один – отключаем один, остальное продолжает работать | в панели провайдера у ключей понятные имена по назначению | Раз в квартал |
| K6 | У ключа минимальные права | Ключ «только чтение одной зоны» при утечке почти безвреден | Cloudflare: токен с ограниченными правами, а не Global API Key; облачное хранилище: ключ на одну корзину (bucket); GitHub: fine-grained токен на один репозиторий | Раз в квартал |
| K7 | У каждого платного провайдера стоит лимит расходов и оповещение | Утёкший ключ ИИ выжигают за часы, а счёт приходит вам | Anthropic: лимиты по workspace в разделе Billing и Rate limits; OpenAI: бюджет проекта; OpenRouter: лимит кредитов на ключ | Раз в месяц |
| K8 | Ключи меняются по плану, например раз в 90 дней | Старый утёкший ключ перестаёт работать сам | дата создания в реестре; у OpenAI можно задать ключу срок действия | Раз в квартал |
| K9 | Вы смотрите статистику использования: всплески, незнакомые модели, активность ночью | Так утечку замечают раньше, чем приходит счёт | страницы Usage и Logs у провайдеров | Раз в неделю |
| K10 | Ключи не попадают в логи, отчёты агентов, чаты и отчёты об ошибках | Логи читают многие люди и программы, в том числе другие агенты | `grep -rcE "sk-ant-\|sk-proj-\|sk-or-\|Bearer [A-Za-z0-9_-]{20,}" logs/ \| grep -v ":0"` – выводит только число совпадений, ждём пустой вывод | Раз в месяц |
| K11 | Агент не видит ключей, которые ему не нужны | Обманутый агент может отдать только то, что у него есть | `env \| cut -d= -f1 \| grep -iE "key\|token\|secret"` в окружении агента – только имена, без значений; чтение папки с секретами запрещено в настройках агента | Раз в квартал |
| K12 | Ключи, которые распоряжаются деньгами и личностями (токен бота, секрет платёжной системы, ключи криптокошельков), хранятся отдельно от остальных | Их утечка – прямые потери денег и репутации, а не просто счёт за API | отдельные файлы и отдельный пользователь системы; если биржа или кошелёк умеет выдавать ключ с урезанными правами (например, только торговля, без вывода), используйте его и проверьте по документации, что он на самом деле не может | Раз в квартал |
| K13 | Написан план «ключ утёк» на одну страницу | В момент утечки некогда думать | документ есть, и все, кто работает с ключами, знают, где он; образец ниже | Раз в квартал |

## Что делать, когда ключ утёк

Порядок важен.

1. Сразу отозвать ключ в панели провайдера. Удаление ключа из git не помогает: его уже могли скопировать.
2. Выпустить новый ключ, обновить его на сервере, перезапустить сервис.
3. Посмотреть Usage и Logs: что успели сделать и на какую сумму. Если были чужие расходы, написать в поддержку провайдера.
4. Найти, как ключ утёк (git, лог, отчёт агента, заражённый пакет), и закрыть этот путь.
5. Если заражён компьютер или установленный пакет, менять все ключи, которые там были, а не один.
6. Записать в реестр: дата, причина, что изменили.

## Оговорки

- Доступен ли secret scanning бесплатно для приватных репозиториев, зависит от тарифа GitHub: проверьте в настройках своего репозитория.
- Флаги `gitleaks` не сверены с документацией построчно: если команда не сработала, посмотрите `gitleaks --help`.
