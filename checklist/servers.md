# Серверы, сеть, бэкапы и API

Сервер – компьютер в дата-центре, на котором работает ваш сайт, бот или агент. Его круглосуточно прощупывают автоматические программы: ищут открытые двери, подбирают пароли. Большая часть пунктов ниже закрывает именно такие массовые атаки.

Команды рассчитаны на Linux (Ubuntu или Debian). Часть из них требует прав администратора (`sudo`); если вы не уверены, что делает команда, сначала прочитайте её описание. Команды написаны по документации; попробуйте их на одном сервере, прежде чем проверять все.

## Сервер и сеть

| № | Что | Зачем | Как проверить | Как часто |
|---|-----|-------|---------------|-----------|
| S1 | Вход по ssh (удалённое управление сервером) только по ключу, без пароля и без пользователя root | Пароли подбирают боты круглосуточно | `sudo sshd -T \| grep -E "passwordauthentication\|permitrootlogin\|pubkeyauthentication"` – ждём `passwordauthentication no`, `permitrootlogin no` | Раз в месяц |
| S2 | В списке ssh-ключей на сервере только известные вам ключи | Забытый ключ бывшего подрядчика – открытая дверь | `awk '{print $NF}' ~/.ssh/authorized_keys` – покажет подписи ключей; сверить со своим списком | Раз в квартал |
| S3 | Файрвол (фильтр входящих соединений) пропускает только нужные порты, обычно 22, 80 и 443 | Остальные службы не видны из интернета | `sudo ufw status verbose`; с другого компьютера `nmap -Pn адрес-сервера` | Раз в месяц |
| S4 | Базы данных и внутренние сервисы слушают только локальный адрес `localhost` (доступны только с самого сервера) | Postgres, Redis, панели управления и служебные API не должны быть видны из интернета | `ss -tlnp \| grep -vE "127\.0\.0\.1\|\[::1\]"` – в списке только веб-сервер и ssh | Раз в месяц |
| S5 | Включены автообновления безопасности (unattended-upgrades) | Дыры в системе закрываются без вашего участия | `systemctl is-enabled unattended-upgrades`; `cat /etc/apt/apt.conf.d/20auto-upgrades`; файл `/var/run/reboot-required` означает, что нужна перезагрузка | Раз в месяц |
| S6 | fail2ban или аналог (блокирует адрес после нескольких неудачных попыток входа) | Срезает перебор паролей и шум в логах | `sudo fail2ban-client status sshd` | Раз в месяц |
| S7 | Сервисы работают не от root, каждый от своего пользователя | Взлом одного сервиса не открывает весь сервер | `ps -eo user:20,comm --no-headers \| sort \| uniq -c \| sort -rn`; поле `User=` в файлах служб systemd | Раз в квартал |
| S8 | Права на файлы с секретами: папка 700, файлы 600 (читает только владелец) | Другой пользователь или процесс на сервере не прочитает ключи | `stat -c "%a %U %n" .env* путь-к-папке-с-секретами/*` – смотрим только права и имена, не содержимое | Раз в месяц |
| S9 | Бэкапы (резервные копии) есть, лежат вне сервера и зашифрованы | Взлом или поломка сервера не уничтожит данные вместе с копиями | список копий в хранилище, дата последней; `crontab -l \| grep -iE "backup\|dump\|restic\|rclone"` | Раз в неделю |
| S10 | Учебное восстановление из бэкапа | Копия, которую ни разу не пробовали развернуть, не считается копией | развернуть копию в тестовую базу и сравнить число строк в главных таблицах | Раз в квартал |
| S11 | Конфиги веб-сервера (Caddy, nginx) лежат в git, выкладка с резервной копией и откатом | Любое изменение видно и обратимо | `git log` репозитория с конфигами | При каждом изменении |
| S12 | Оповещения: вход по ssh, сервис упал, кончается диск, всплеск ошибок 4xx и 5xx | Взлом замечают за минуты, а не через месяц | отправить тестовое событие и убедиться, что оно пришло (в мессенджер, на почту) | Раз в месяц |
| S13 | Логи (журналы событий) хранятся 30 дней и больше и копируются вне сервера | Взломщик первым делом чистит логи | `journalctl --disk-usage`; настройки ротации логов | Раз в квартал |
| S14 | Сверка с CIS Benchmark (эталонный список безопасных настроек системы) | Находит сотни мелких слабых мест разом | `sudo lynis audit system` (бесплатный сканер); `ssh-audit адрес-сервера` | Раз в квартал |

## API и база данных

| № | Что | Зачем | Как проверить | Как часто |
|---|-----|-------|---------------|-----------|
| A1 | Каждый запрос к API проверяет не только «кто ты», но и «твой ли это объект» | Первое место в OWASP API Top 10: меняешь номер заказа в адресе и видишь чужой заказ | тест: пользователь А запрашивает заказ пользователя Б – ждём ответ 403 или 404 | При каждом релизе |
| A2 | Лимит частоты запросов на вход, оплату и вызовы ИИ | Защита от перебора паролей и от счёта за чужие запросы к ИИ | `for i in $(seq 60); do curl -s -o /dev/null -w '%{http_code}\n' https://api…/health; done \| sort \| uniq -c` – ждём хотя бы один ответ 429 (слишком много запросов) | При каждом релизе |
| A3 | Автоматическая документация API (`/docs`, `/redoc`, `/openapi.json` во FastAPI и похожих фреймворках) закрыта в рабочей версии | Не отдаём посторонним карту всех адресов API | `for p in docs redoc openapi.json; do echo "$p $(curl -s -o /dev/null -w '%{http_code}' https://api…/$p)"; done` – ждём 404 | При каждом релизе |
| A4 | Supabase: RLS (Row Level Security – правила, кто какие строки таблицы видит) включён на всех таблицах, правила осмысленные | Публичный ключ Supabase есть у всех посетителей сайта; без RLS таблицу читает любой | Security Advisor в панели Supabase; SQL-запрос `select schemaname, tablename from pg_tables where schemaname='public' and not rowsecurity;` – ждём пустой ответ | При каждом релизе |
| A5 | Supabase: обязательный SSL, сетевые ограничения, двухфакторный вход у всех участников, больше одного владельца | Это официальный чек-лист Supabase перед запуском | панель Supabase: Database Settings, Organization Team | Раз в квартал |
| A6 | Уведомления платёжной системы (webhook – запрос, которым она сообщает вашему серверу «оплата прошла») проверяются по подписи, повтор уведомления не выдаёт доступ дважды | Иначе любой отправит «оплата прошла» и получит доступ бесплатно | запрос без подписи (у CloudPayments заголовок `Content-HMAC`) и с неверной подписью – ждём отказ; тест на повторное уведомление | При каждом релизе |
| A7 | Сумма и товар берутся с сервера, а не из браузера | Покупатель не сможет поменять цену в запросе | просмотреть код создания платежа; тест с изменённой суммой | При каждом релизе |
| A8 | Webhook Telegram-бота защищён секретным токеном (`secret_token`), адрес webhook не угадывается | Посторонний не сможет слать боту поддельные сообщения | запрос на адрес webhook без заголовка с секретом – ждём отказ | При каждом релизе |
| A9 | Ошибки не показывают трассировку (подробный отчёт об ошибке с путями и кодом) и внутренности | Меньше подсказок взломщику; неправильная обработка ошибок вошла в OWASP Top 10 2025 | `curl -s -X POST https://api…/ -d '{bad' \| head -c 400` – в ответе нет путей к файлам и кусков кода | При каждом релизе |
| A10 | Python: версии пакетов зафиксированы (`==` у каждого), `pip-audit` чистый | В марте 2026 заражённая версия litellm провисела в PyPI (каталоге пакетов Python) около 40 минут; пострадали те, кто ставил пакет без фиксации версии | `pip-audit -r requirements.txt`; `grep -cvE "==\|^#\|^$" requirements.txt` – ждём 0 | Раз в неделю |

## Оговорки

- Флаги команд `fail2ban-client`, `lynis`, `pip-audit` не сверены с документацией построчно: если команда не сработала, посмотрите `команда --help`.
- Заголовок `secret_token` у webhook Telegram-бота и отсутствие встроенного лимита частоты в Caddy тоже не сверены с конкретной страницей документации. Перед настройкой сверьтесь с документацией Telegram Bot API и вашего веб-сервера.
